# 上传时发布选牌与对战的关联

2026-10-31，模式：实现。

目标：关联是上传数据的一部分，不仅在本机网页上临时计算。上传前建立并验证关系，
上传后从远端逐字节读回，只有校验成功才保存本机发布回执。

允许修改：轮抽上传格式、发布器、后台重试触发、关联读取及笼统提示。
保留逐手原始事实、旧账号归属、既有私有仓库、非强推和共享锁，不补造缺失对战，
不迁移旧记录，不改动无关并行开发。

## 协议与发布顺序

- `drafts/index.json` 使用可读取旧 V1 的 V2 格式，每账号增加 bindings 描述符
  （固定路径、字节数、SHA256、条数）。
- 每账号 `drafts/accounts/<account_key>/bindings.json` 保存关联或具体待处理状态。
  每条关联绑定逐手来源指纹、赛事完整牌池、已核验的对战版本／提交、
  主牌组证据和账号。重复来源保留全部 ID。
- 保持原逐手对象格式与不可变对象路径不变；未知账号观察不上传。
- 上传前以远端已有比赛索引、manifest 内容哈希、coach 与 cards 文件字节校验比赛版本。
  对当前完整原始回放重新规范化生成，与远端完整内容哈希比较，不凭迁移同步回执认定一致。
  已有生成缓存只有在“完整原始回放哈希、实际生成内容哈希、历史路径”三者同时一致时才复用；
  失配就重新生成，保持远端原有 multipart 格式。该缓存是本机实际生成映射，不是签名证明，
  不防范用户故意篡改自己的缓存；不从推测的迁移回执构造这份映射。
  尚未上传或本地／远端版本不一致的比赛，不假装已关联。
- 完整牌池相等、候选与选择连续、赛事唯一、对战主牌组佐证等规则沿用
  `DRAFT_BINDING.md`。上游 bytes 不符属于发布失败，不降级成成功的待关联记录。
- 初始只选完牌、尚未打比赛时，逐手记录与“暂无对战”状态照常上传。
  后来对战发布完成会再次发布关联；没有新选牌也可更新关系。
- 远端 readback 成功后，本机保存同一份关联清单和回执。网页优先消费该份已发布结果；
  清单或来源指纹无效时不显示虚假的已关联状态。历史未升级时保留旧的本地推导兼容。

## 自动补全

逐手观察变化、已归档对局／增量赛事资料变化或比赛上传状态变化，都会触发后台重试。
对战同步完成也执行关联发布；关联失败单独报告部分完成，不把已上传对战回滚。
每个动作使用既有共享同步锁；断网、push 回执丢失和并发更新不删除本地来源，不 force push。
发布开始前记录输入版本；发布期间新增资料不能被误标成已处理，仍触发后续补全。
少数比赛已关联但尚有比赛待上传时，显示具体待处理场数，赛事总战绩不标为已核验。
昂贵的历史规范化在独立工作线程或采集进程执行，不阻塞 Viewer 主线程。
